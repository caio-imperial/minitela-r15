    Texture.acf visto pelo código-fonte do SDK 1.10.20 (GC9002)¶

    Este arquivo é a leitura do firmware (lado device) do formato .acf. Complementa RE-acf.md (que é a leitura do compilador e da bancada) e RE-firmware.md (flash/NOR). Não substitui nenhum dos dois.

    Fonte primária (doravante LIB/ e CS/):

    apelido caminho
    LIB/ .tools/vendor/sdk120/v1.10.20_2025.07.02_GC9002/GC9002/GC9002/GC9002LIB/
    CS/ .tools/vendor/sdk120/v1.10.20_2025.07.02_GC9002/GC9002/CommonSource/
    EX/ .tools/vendor/sdk120/v1.10.20_2025.07.02_GC9002/U盘_480x272_CTP/Texture.acf (amostra real, 480x272)

    Todas as afirmações abaixo têm arquivo:linha. O que não tem, está marcado hipótese ou não documentado. Nada foi executado e nada foi gravado no device: a única coisa que rodou foi aritmética em Python sobre bytes da amostra EX/.

    Resumo executivo¶

    1. O firmware não valida o checksum do arquivo (campo +4). Ele valida três coisas: StartOfConfigdata % 16384 == 0, MagicNumber == 0x494d4841 ("AHMI") e AHMIInfo.Version == AHMI_CPU1_VERSION (0x5A010a13) — CS/AHMI/FileLoad.cpp:570, :582, :589.
    2. Mas ele valida um checksum por página, e isso é o que RE-acf.md não viu: CheckCode == 0xA55A5AA5 ^ XOR(words do bloco da página) — CS/Main/AHMIInterface.cpp:1421
    3. CS/AHMI/validation.cpp:75. Provado contra as 9 páginas da amostra real. O laço de leitura é do{...}while(checkCode != newPage->CheckCode) (:1387–:1423): em caso de divergência ele não sai nunca. É a explicação mecânica da "região crítica" do FATO 7.
    4. O "header" do arquivo não é magic+count: é u32 StartOfConfigdata seguido de u32 checksum, u32 ?, e uma string de projeto. O "magic 0x8000 / count" do FATO 6 é o mesmo u32 lido como dois u16. E a "região crítica" de 772392–801200 (FATO 7) é simplesmente tudo a partir de StartOfConfigdata (802816 no .acf de fábrica), porque ali começa a config que o CheckCode cobre.
    5. A "tabela de recursos" que faltava existe e é legível: TextureClass[totalNumOfTexture], 48 bytes por registro, dentro do bloco de cada página, com SingleSliceSize, TexAddr, mTexAttr, TexWidth, TexHeight, … — CS/AHMI/TextureClass.h:59, CS/AHMI/DynamicPageClass.cpp:180. SingleSliceSize em bytes = ceil(w/4)*ceil(h/4)*16 (conferido em 3 texturas reais).
    6. O decodificador de bloco está no fonte, e confirma o FATO 5, com uma ressalva: aquilo é o modo STCRGBA888 (CS/AHMI/Simulator/stc.cpp:629). Existe um segundo modo, STCRGB888, com layout diferente (pesos de 5 bits a partir do bit 49, stc.cpp:723). O acf_codec.py do repo implementa só o primeiro.
    7. A interpolação real não é peso/15: é (w + w/8)/16 com saturação (idem (w+w/16)/32 no modo RGB). Diferença de ~5% no meio da rampa.
    8. O "1 byte/pixel" cai do próprio formato: 240×240 = 57.600 B = os 57.600 B medidos no FATO 4. O slot de imagem do FATO 7 é o formato de blocos; "lixo verde" é sintoma de escrever o sub-formato errado (hipótese, ver §2.5).

    1. Como o firmware carrega e valida o Texture.acf¶

    1.1 Onde o arquivo mora na flash¶

    GC9002 não tem "flash de textura" separada: o .acf está no mesmo QSPI mapeado em 0x08000000 que o código, e é lido por XIP (dereference byte a byte).

    o que endereço fonte
    base da região de config 0x080F0000 CS/Main/AHMIInterface.h:77 (ROM_CONFIG_BASE_ADDR)
    upg_cfg.bin +0x7000 = 0x080F7000 LIB/projects/Bootloader/Source/Upgrade/adapt/upgrade_ci.h:116
    CONFIG_START_ADDRESS +0x8000 = 0x080F8000 upgrade_ci.h:114 (recebe cpu0_config.bin, upgrade_ci.h:156)
    calibração de touch +0xB000 CS/Main/AHMIInterface.h:95
    store tags (u32) +0xD000 AHMIInterface.h:89
    product.bin +0xF000 AHMIInterface.h:83
    início do .acf ROM_CONFIG_BASE_ADDR + 0x10000 = 0x08100000 CS/AHMI/csi_ahmi/csi_ahmi.h:39-40
    fim da área de textura 0x08400000 (3 MB) upgrade_ci.h:82 (TEXTURE_FLASH_MAX_ADDR)
    backup do bootloader 0x083C0000 upgrade_ci.h:84-85

    TEXTUREFLASH_START_ADDR = TEXTURE_START_ADDR_FOR_GPU = 0x08100000 e TEXTURE_ADDR_OFFSET = TEXTUREFLASH_START_ADDR - 0x08000000 = 0x10000 (csi_ahmi.h:41). Consequência prática: TexAddr gravado no .acf é offset de arquivo, e o endereço que o GPU recebe é 0x08100000 + TexAddr (CS/AHMI/TextureClass.cpp:791).

    Leitura: csi_ahmi_SeekReadConfigDataAddr(a) só faz base = 0x08100000 + a (CS/AHMI/csi_ahmi/csi_ahmi.c:915-922); csi_ahmi_ReadConfigData chama csi_hal_extern_flash_read (:908), que em GC9002 é gc9002_hal_internal_flash_read (CS/csi_hal/csi_hal_driver/csi_hal_driver_flash.c:516) — um for de leitura de byte em addr+i com espera do bit de busy do CQSPI (:185-200). Não há comando de leitura por chunk.

    Nota: LIB/projects/AHMI_SW/.../GClib/src/texture_flash.c (o DRAM_CACHE/QSPI2/NAND) é código de biblioteca multi-chip; no GC9002 o caminho usado é o acima. O ext_flash_gzip_self_adaption() (texture_flash.c:366), que procura "AHMI" em 0x20 e em 0x40000, está desligado (texture_flash.c:137, comentado).

    1.2 A sequência exata (LoadConfigData, ramo EMBEDDED)¶

    CS/AHMI/FileLoad.cpp:542-608. Para CHIP_GC9002 (linhas 546-563):

    align_size = 16*1024;            // :548
StartOfConfigdata_Pos = 0;       // :549   (GC9002 nunca usa o caso gzip)

csi_ahmi_SeekReadConfigDataAddr(0);           // :562

if (StartOfConfigdata % align_size != 0) erro; // :570-574

    O outro ramo (#if !defined(CHIP_GC9002), linhas 550-560) usa align_size = 1024 e StartOfConfigdata_Pos = 128*1024-4 quando DRAM_CACHE->Gzip_EN — formado o ConfigData&TextureCMP.acf. No GC9002 esse caminho não existe: vector gzip de arquivo inteiro é coisa de GC9003/GC9005.

    1.3 O que é validado, e o que não é¶

    campo validado? onde
    u32 @0 (StartOfConfigdata) múltiplo de 16 KB sim FileLoad.cpp:570
    u32 @4 (checksum do arquivo) não — nenhum leitor no SDK consome esse campo. grep StartOfConfigdata só acha FileLoad.cpp e o bootloader; nada lê +4 —
    u32 @8 não lido por ninguém —
    string de projeto @12 não lida pelo firmware (o bootloader lê versões dentro do ConfigInfo, em StartOfConfigdata+92/+124) upgrade_ci.h:133-135, upgrade_c1.c:1232-1273
    MagicNumber (ConfigInfo+32) sim FileLoad.cpp:582
    AHMIInfo.Version sim, igualdade exata com AHMI_CPU1_VERSION FileLoad.cpp:589, CS/AHMI/Config/AHMICfgDefinition.h:114
    md5_value[32] (ConfigInfo+0) não — só existe a declaração, CS/AHMI/DynamicPageCfgClass.h:96; nenhum uso no código —
    CheckCode de cada página sim, e é fatal AHMIInterface.cpp:1421

    AHMI_CPU1_VERSION = 0x5A010a13 (AHMICfgDefinition.h:114). A amostra EX/ traz exatamente 0x5a010a13 em ConfigInfo+260 — ou seja, o .acf e o firmware têm que ser do mesmo build do gerador, senão o aparelho não carrega.

    Falha em qualquer um dos três testes → startAHMI() entra em for(;;) DrawFivePointPage(...) (CS/Main/AHMIInterface.cpp:686-732): a tela dos cinco pontos vermelhos, para sempre. No GC9002 o Feed_WDG1() está dentro de #if defined(CHIP_GC9005) e o else faz i++ duas vezes (:717-726) — laço deliberadamente infinito.

    Falha de CheckCode é diferente: o do{}while de AHMIInterface.cpp:1387-1423 relê o mesmo endereço para sempre (a leitura é XIP, o valor nunca muda). CPU1 trava. Hipótese para o "reinicia em ciclo" do FATO 7: o CPU0 (MCU principal) tem watchdog próprio e reseta o conjunto quando o CPU1 para de responder.

    1.4 O header, campo por campo¶

    Medido em EX/ (480×272, 737.288 B) e conferido contra o struct:

    offset tipo valor em EX/ significado
    +0 u32 LE 0x000B0000 = 720896 StartOfConfigdata: offset a partir do byte 0 do arquivo até o ConfigInfoClass. Múltiplo de 16 KB.
    +4 u32 LE 0x1D99EAB8 checksum: XOR de todas as words de 32 bits do arquivo, exceto ele mesmo e a última word (ver §3.6)
    +8 u32 LE 0x00054950 = 346448 não documentado. Observação: é exatamente TotalTextureSize/2 (692896/2) nesta amostra. Não é lido por firmware nem bootloader.
    +12 char[] "480x272_demo1753175099001" identificação do projeto (texto, terminado em NUL, o resto até 0x4000 é zero)
    +0x4000 — blocos STC início da área de textura (offset físico, não tabelado)
    StartOfConfigdata — ConfigInfoClass ver §3.2
    EOF-4 u32 0xA55A5AA5 footer obrigatório (entra no XOR acima)

    Consequência aritmética (bate com o FATO 2): tamanho_do_arquivo = 8 + k*16384 (EX/: 8 + 45×16384 = 737288). O +8 é o header; todo o resto é grade de 16 KB.

    1.5 Como o firmware consome a config depois disso¶

    InitialAHMIStruct (AHMIInterface.cpp, a partir de ~:1000):

    • páginas: NumofPages registros de sizeof(DynamicPageCfgClass) lidos em sequência a partir de StartOfConfigdata + 284 + CfgStringSize (:1208 dá a posição corrente, :1223 e :1356 fazem o seek, :1489 pula o array);
    • o bloco de dados de cada página fica em StartOfConfigdata + StoreOffset (:1363, DynamicPageClass.cpp:697) e tem TotalSize bytes;
    • os TotalNumOfTexture registros de textura ficam dentro desse bloco (§2.1);
    • sons: mStartAddr é offset e vira 0x08100000 + mStartAddr (:1508-1512);
    • pages com fundo STCRGBA888 guardam TexAddr | 0x80000000 no array de fundos (:1458-1470, o | 0x80000000 em :1469) — o bit 31 é o flag "STC com alpha" (§2.2).

    2. As 3 imagens custom e o formato de pixel¶

    2.1 Onde a informação está (a "tabela de recursos")¶

    Cada página tem seu próprio bloco de dados, com layout fixo definido em DynamicPageClass::InitPage (CS/AHMI/DynamicPageClass.cpp:155-195):

    bass + 0                                    CanvasClass        [NumOfCanvas]
     + NumOfCanvas*|Canvas|                 SubCanvasClass     [NumOfSubCanvas]
     + NumOfSubCanvas*|Sub|                 WidgetClass        [NumOfWidget]
     + NumOfWidget*|Widget|                 AnimationKeyFrame  [mNumOfAnimationKeyFrames]
     + mNumOfAnimationKeyFrames*|AKF|       AnimationAction    [mNunOfAnimationActions]
     + ...*|AA|                             u8 actionInstr      [ActionInstructionsSize]
     + ActionInstructionsSize               >>> TextureClass   [totalNumOfTexture]  <<<
     + totalNumOfTexture*48                 touchWidgetRange   [NumofTouchWidget]
     + ...                                  u16 gifWidgetList  [NumofGifWidget]
     + ...                                  u16 pageAction     [NumOfPageAction]
     + ...                                  u16 canvasAction   [NumOfCanvasAction]

    Citação: pBasicTextureList = (TextureClass*)(pActionInstructions + mActionInstructionsSize) (DynamicPageClass.cpp:180). O bloco é exatamente TotalSize bytes e começa em StartOfConfigdata + StoreOffset.

    TextureClass (CS/AHMI/TextureClass.h:59-90, sem métodos virtuais ⇒ sem vtable, sizeof = 48 com VERSION_2) — layout observado e confirmado em arquivo real:

    off tipo campo
    0 u32 SingleSliceSize — bytes de uma fatia
    4 u32 TexAddr — offset no .acf (se &0xF0000000 == 0)
    8 u32 SliceFlagsHeaderAddr — 0 = sem color-slice; ≠0 = tabela de flags
    12 u32 mTexAttr — bits 7-4 = tipo (§2.2), bit 3 mask, 8 ADDRTEXTURE, 15 DRAWING, … (drawImmediately_cd.h:222-300)
    16 u16 TexWidth
    18 u16 TexHeight
    20 u16 FocusedSlice
    22-34 s16×7 OffsetX/Y, RotateAngle, ShearAngleX/Y, ShearAngleZX/ZY
    36,38 s16 ScalerX/Y (1.9 fixo: 512 = 1.0)
    40-43 s8×4 TexLeft/Top/Right/ButtomTileBox
    44 u8 staticTexture (fatias por bloco de 16 KB; 0 = sem entrelaçamento)
    45 u8 useCanvasPoint
    46-47 — padding

    Receita para achar a tabela sem conhecer |Widget|: quando NumofTouchWidget, NumofGifWidget, NumOfPageAction e NumOfCanvasAction são 0 (caso comum), início_da_tabela = TotalSize - totalNumOfTexture*48.

    Verificado na página 6 da amostra EX/ (StoreOffset=4480, TotalSize=3252, totalNumOfTexture=12 → tabela em 3252-576 = 2676):

    # SingleSliceSize TexAddr attr tipo W×H conferência
    0 0 0xFFFFFFFF 0x00000130 3 = PURECOLOR 480×272 fundo chapado
    1 2912 0x000A53C0 0x00000110 1 = STCRGBA888 104×26 26×7×16 = 2912 ✓
    2 16 0x000A6A80 0x00000110 1 4×4 1×1×16 = 16 ✓
    11 13312 0x000A6AA0 0x00000110 1 254×51 64×13×16 = 13312 ✓

    Isso prova duas coisas de uma vez: o tamanho de uma textura é ceil(w/4)*ceil(h/4)*16, e texturas não são alinhadas a 16 KB entre si (0xA53C0 % 0x4000 = 5056). Só o container e o StartOfConfigdata são.

    2.2 O codec: "STC", 16 B por bloco 4×4, dois sub-formatos¶

    Os tipos no GC9002 (CS/AHMI/drawImmediately_cd.h:222-249, ramo CHIP_GC9002):

    STCRGB888   0x00     <- blocos de 16 B, SEM alpha
STCRGBA888  0x10     <- blocos de 16 B, COM alpha
ALPHA1 0x20  PURECOLOR 0x30  RGB565 0x40  RGBA8888 0x50  Y8 0x60
RGB565_RE 0x70  PUREMASK 0x80  ALPHA2 0x90  ALPHA8 0xa0  ALPHA4 0xb0
ARGB1555 0xc0  ARGB4444 0xd0  SFBC 0xe0  RGBA8888_RE 0xf0

    No GC9002 0x00/0x10 são STC, não DXT1/DXT5: no simulador de GPU ahmi::cache() o SIM_DXT1 (código 0) do GC9003 é trocado por stc_rgb_dec() quando embedded_platform != EMBEDDED_GC9003 (CS/AHMI/Simulator/ahmiv3.cpp:825-875, chamada em :872). O tipo que o hardware recebe é TexType = (texture_ctrl & 0x1e) >> 1 (ahmiv3.cpp:1257).

    Os decodificadores:

    função arquivo:linha quando
    stc_rgba_dec stc.cpp:706-721 tipo 0x10 (STCRGBA888)
    stc_rgb_dec stc.cpp:1189-1201 tipo 0x00 (STCRGB888)
    stc_rgba_one_partition_dec stc.cpp:629-658 é o FATO 5
    stc_rgb_one_partition_dec stc.cpp:723-747 modo 0 do RGB, layout diferente

    O bit 0 escolhe a partição (stc.cpp:1190-1201):

    bit0 == 0        -> one partition          (o "modo 0" do RE-acf.md)
& 0x3 == 0x1     -> two partition          (RGBA) / two plane two partition (RGB)
& 0x7 == 0x3     -> two plane two partition (RGBA) / two partition (RGB)
& 0xf == 0x7     -> two plane one partition
senão            -> three partition

    2.3 Layout de bits — confirmação e correção do FATO 5¶

    stc_rgba_one_partition_dec (stc.cpp:629-658) — bitstream LSB-first:

    bits campo
    0 flag de partição (0 = one partition)
    1-8 / 9-16 R0 / R1
    17-24 / 25-32 G0 / G1
    33-40 / 41-48 B0 / B1
    49-56 / 57-64 A0 / A1
    65+4i (i=0..15) peso de 4 bits do pixel i (o 16º só tem 3 bits reais — ver abaixo)

    Interpolação (stc.cpp:2-9): tw = w + w/8; c = clamp(a0 + (a1-a0)*tw/16).

    stc_rgb_one_partition_dec (stc.cpp:723-747) — sem alpha, pesos de 5 bits:

    bits campo
    0 flag de partição
    1-8 / 9-16 R0 / R1
    17-24 / 25-32 G0 / G1
    33-40 / 41-48 B0 / B1
    49+5i (i=0..15) peso de 5 bits; w' = w + w/16; c = clamp(a0 + (a1-a0)*w'/32) (stc.cpp:11-18)

    Orçamento de bits — e é aqui que o FATO 5 acertou em cheio:

    • RGBA: o 16º peso começa no bit 125 e só tem 3 bits reais (125, 126, 127; o bit 128 não existe no u128, então weight_table>>60 entrega 3 bits + zero). Peso máximo do pixel 15 = 7. É exatamente o "o peso do pixel 15 nunca passa de 7" medido.
    • RGB: 49 + 16×5 = 129 > 128 — o 16º peso começa em 124 e tem 4 bits (0..15 de uma faixa 0..31), não 3.

    y*4+x é a ordem raster dentro do bloco (stc.cpp:739, :649).

    Prova de que o FATO 5 é o modo RGBA: o bloco que o compilador do ODM gerou para 16 tons de cinza — fe 01 fe 01 fe 01 fe ff df 9b 57 13 cf 8a 46 02 (FATO 5) — decodificado com stc_rgba_one_partition_dec dá pesos 15,14,13,…,0 e R = 0,15,31,47,63,79,95,111,143,159,175,191,207,223,239,255 (rampa monotônica). Decodificado com o modo RGB (5 bits no bit 49) dá lixo (pesos 31,31,31,31,30,6,15,21,9,28,25,10,20,17,4,0).

    Correção ao FATO 5 (única diferença real): a fórmula não é c0 + (c1-c0)*w/15 mas c0 + (c1-c0)*(w + w/8)/16. Para w=15 o fator é 135/128 (satura); para w=7 é 63/128 = 0,492, contra 7/15 = 0,467 — ~5% de erro no meio da rampa. Um encoder que queira bater a imagem tem que inverter a função real, não w/15. Hipótese (não provada em silício): interpolate() é o modelo de referência de uma tabela de hardware; se o ASIC fizer exatamente w/15, o gerador é que estaria "errado". Os 16 níveis do teste acima são compatíveis com as duas leituras, então a única forma de decidir é medir luminância na tela ou achar a LUT no RTL.

    2.4 SingleSliceSize, fatias e o 16 KB¶

    TextureClass.cpp:785-793 calcula o deslocamento da fatia:

    if (staticTexture == 0)
    addr = FocusedSlice * SingleSliceSize;
else
    addr = 0x4000*(FocusedSlice/staticTexture) + (FocusedSlice%staticTexture)*SingleSliceSize;
TexAddr_final = TexAddr + addr + TEXTURE_ADDR_OFFSET;   // se (TexAddr & 0xF0000000)==0

    staticTexture = "quantas fatias cabem em um bloco de 16 KB" — é o único lugar em que o 16 KB aparece dentro da textura. img_align() (TextureClass.cpp:80-172) é a contraparte no gerador: escolhe a largura da fatia para que (w+3)/4*4 * (h+3)/4*4 <= 16*1024 - 64 — os 64 bytes são cabeçalho de fatia (relacionado a SliceFlagsHeaderAddr). Para uma textura "normal" (não animada), SingleSliceSize é o tamanho da imagem inteira e staticTexture = 0, como se vê nos 12 registros da página 6 da amostra.

    2.5 Onde estão as 3 imagens custom — o que dá para afirmar¶

    Fato aritmético: uma imagem 240×240 em STC ocupa 60×60×16 = 57.600 bytes = 1 B/px. É exatamente a região de 57.600 B em 685992 que o FATO 4 mediu. Portanto o slot de imagem do FATO 4 é o formato de blocos, e a conclusão do FATO 7 ("a região das imagens custom não usa o formato de blocos") está contradizida por aritmética e pelo fonte.

    O que continua não documentado: os offsets exatos dos 3 slots no Texture.acf de fábrica 240×240 — esse arquivo não está no repo nem no pacote do SDK, então não deu para ler a tabela. O procedimento para obtê-los em 5 linhas de Python está em §5; ele não depende do compilador do ODM.

    Hipóteses para o "lixo verde" do FATO 7 (as duas explicam o mesmo sintoma):

    1. sub-formato trocado: escrever blocos no layout RGBA (pesos de 4 bits no bit 65) numa textura cujo registro diz tipo 0x00 (RGB, pesos de 5 bits no bit 49) — ou vice-versa. Como 1 byte/px é o mesmo, o tamanho bate e o resultado é ruído colorido;
    2. widget do tipo GIF: o firmware trata widgets de pGifWidgetList à parte (AHMIInterface.cpp:400-450), e nesse caso o dado não é a textura crua e sim um bloco comprimido com LUT: u32@bloco com lutSize = valor>>12 (KB), em bloco + lutSize*1024 a string "AHMI" e, logo depois, os primeiros 32 B comprimidos que decompress_first256bytes() expande para o BlockHeader de 28 B (nome "GIF", w, h, textType, texaddr, singlesliceSize, picnum, delay, res) — CS/gziplib/gzipBlock.cpp:39-91, gzipBlock.h:26-38, gzip.cpp:1272-1289. Cada frame começa em 0x20 + n*SinglesliceSize (AHMIInterface.cpp:435, :439-443). Escrever STC cru no início do bloco estraga o header comprimido → lixo.

    Para decidir, basta ler o registro de textura do widget correspondente: se attr>>4 for 0x1/0x0 é textura crua; se o widget estiver em pGifWidgetList, é bloco LUT.

    2.6 O compressor (o que o fonte não tem)¶

    Não existe encoder STC no SDK: grep -rn "stc_.*enc\|STC_ENC" em CommonSource/ não retorna nada. O SDK entrega o decodificador (simulador de GPU) e o container; a compressão continua sendo o que o acf_codec.py já faz. Bom para o repo: a codificação do FATO 5 é o lado que não precisa mais ser descoberto.

    3.4 Os dois checksums (um ignorado, um fatal)¶

    (a) checksum do arquivo, u32 @4 — não é validado por ninguém, mas existe e é fácil de gerar:

    checksum = XOR de todos os u32 LE do arquivo,
           exceto a word em +4 e a última word (footer 0xA55A5AA5)
<=> (XOR de todas as words, incluindo o campo e o footer) == 0xA55A5AA5

    Verificado em EX/: XOR(todas) = 0xA55A5AA5; XOR(sem +4, sem footer) = 0x1D99EAB8 = valor gravado. (As duas formulações do FATO 6 são equivalentes, porque o footer entra no XOR do "tudo".)

    (b) CheckCode de página — é o XORCheck de verdade (CS/AHMI/validation.cpp:75-86):

    u32 XORCheck(u32 *data, u32 datalen) {
    u32 checkCode = 0xA55A5AA5;
    for (i=0; i<datalen; i++) checkCode ^= data[i];
    return checkCode;
}
// chamado com: XORCheck((u32*)PageSpace, TotalSize/4)

    i.e. CheckCode = 0xA55A5AA5 ^ XOR(words do bloco, TotalSize/4), sobre os TotalSize bytes do bloco da página, em StartOfConfigdata+StoreOffset. TotalSize % 4 == 0 em todas as páginas observadas.

    Provado contra arquivo real — as 9 páginas da amostra EX/:

    5. Roteiro para gerar o .acf sem o compilador do ODM¶

    O que o fonte prova ser necessário (tudo gera em Python puro):

    1. Decidir o mapa de texturas. Para cada textura: w, h, tipo (0x00 RGB ou 0x10 RGBA), e o offset TexAddr. Não precisa alinhamento entre texturas; o primeiro offset livre depois do header (0x4000) serve.
    2. Comprimir em STC: ceil(w/4)*ceil(h/4) blocos de 16 B, ordem raster. Modo 0 (bit0=0) é o mais simples; o acf_codec.py já gera o sub-formato RGBA (FATO 5), que é o tipo 0x10. Para 0x00 é preciso o layout de 5 bits (§2.3) — não implementado no repo hoje.
    3. Header: u32 @0 = StartOfConfigdata (múltiplo de 16384, ≥ fim das texturas), @4 = checksum, @8 livre, @12 = nome do projeto.
    4. ConfigInfoClass (284 B) com MagicNumber=0x494d4841, TotalSize = tamanho_final - 8, NumofPages, CfgStringSize, AHMIInfo.Version = 0x5A010a13 da versão do firmware alvo, ScreenWidth/Height.
    5. DynamicPageCfgClass[NumofPages], cfgString, depois os blocos de página, cada um com StoreOffset, TotalSize, CheckCode = 0xA55A5AA5 ^ XOR(words) e a tabela TextureClass[totalNumOfTexture] no fim do bloco (48 B cada).
    6. Footer 0xA55A5AA5 e o checksum do arquivo por último.
    7. Sanidade que o device aplica: StartOfConfigdata % 16384, magic, versão, e CheckCode por página. Tudo o resto é livre.

    Validador mínimo (o que o firmware faz, e nada além):

    assert StartOfConfigdata % 16384 == 0
assert u32(StartOfConfigdata+32) == 0x494d4841
assert u32(StartOfConfigdata+260) == 0x5A010a13      # versão do firmware alvo
for p in pages:                                       # 56 B cada
    blk = data[StartOfConfigdata+p.StoreOffset:][:p.TotalSize]
    assert xor_words(blk) ^ 0xA55A5AA5 == p.CheckCode

    • GifID fica 0 (= GZIPTYPE_Intern | id 0), mas não é usado neste firmware (§7.3).

    7.3 Q3 — os quadros estão crus (STC), não em gzip¶

    Condição de compilação, lida no fonte:

    • o #include do gziplib em Gif.cpp é #ifndef CHIP_GC9002_NoHyper + #if defined(CHIP_GC9002) (Gif.cpp:17-28);
    • mas toda a lógica de bloco comprimido está sob #ifdef USE_GZIP_LIB (Gif.cpp:203-259), e em projects/AHMI_SW/Source/ahmi/app/platform.h:42 a macro está comentada: //#define USE_GZIP_LIB. Idem AHMIInterface.cpp (tarefa de 10 ms).
    • não existe macro texture_gif no fonte; o que decide é USE_GZIP_LIB.
    • CHIP_GC9002_NoHyper só retiraria o #include; o caminho gzip depende de USE_GZIP_LIB de qualquer forma.

    Com USE_GZIP_LIB ligado, GifID != 0xFFFF faria o widget buscar getGzipBlockInfo(GifID & 0x7FFF, GifID>>15) e o dado seria um bloco LUT: u32@bloco com lutSize = valor>>12 (KB), "AHMI" em bloco + lutSize*1024, header comprimido de 32 B e cada quadro em 0x20 + n*SinglesliceSize (CS/gziplib/gzipBlock.cpp:39-91, Main/AHMIInterface.cpp:435-443). Não é o caso aqui.

    Provas no arquivo:

    • não existe a string "AHMI" nem "GIF" em [0xA77B0, 0x4C62B0);
    • os 75 quadros têm exatamente 75 × 57.600 = 75 × 3600 × 16 bytes;
    • no quadro 0, 3600 de 3600 blocos têm bit0 = 0 (STC one-partition, §2.3).

    7.4 O trailer de fatias (SliceFlagsHeaderAddr)¶

    É o que o §2.4 chamava de "tabela de flags" e nenhum arquivo da amostra usava. Layout lido de TextureClass.cpp:565-567 + getSliceRealOffsetWithFlags (:441-514):

    +0  u32  flagsAddr   = trailer+8
+4  u32  colorsAddr  = trailer+8+(2*ceil(nfatias/16))
+8  u16[ceil(n/16)]  bitmap: bit i = 1 -> fatia i é imagem; 0 -> fatia i é cor
..  área de cores (2*ceil(n/16) bytes nos arquivos medidos; ver ressalva)
padding com zero até múltiplo de 16

    Detalhes que morderam:

    • esses dois primeiros u32 são gravados como dois u16 little-endian, e lidos de volta por readU32FromTextureBuffer como (arr[0]<<16)|arr[1] (:377-399). Ex.: 4c 00 b8 62 → 0x004C62B8. Não é u32 LE nem BE "de livro".
    • o bitmap é lido MSB-first dentro de cada u16 (readBitFromTextureBuffer, :401-439).
    • tamanho: 8 + 4*ceil(n/16) arredondado para 16 B. Dá 16 B para n ≤ 32, 32 B para 33 ≤ n ≤ 96, 48 B para 97 ≤ n ≤ 112… É por isso que o trailer do slot 1 passa de 16 para 32 bytes com 75 fatias, e o das páginas 5/6 continua 16.
    • em getSliceRealOffsetWithFlags o retorno é o índice denso da fatia imagem (conta os bits 1 até FocusedSlice e subtrai 1) — com todas as fatias imagem, o resultado é o próprio índice, e addr = realOffset * SingleSliceSize (:750-765).
    • ressalva: nenhum arquivo analisado tem fatia de cor, então o formato exato da área de cores (2 bytes por 16 fatias no trailer × leitura u32 em colorsAddr + idx*4, :777) não foi exercitado. Para GIF (todas as fatias imagem) basta zerar essa área.

    Conteúdo medido em 0x4C62B0: 4c 00 b8 62 | 4c 00 c2 62 | ff ff ff ff ff ff ff ff e0 ff | 00… → flagsAddr 0x4C62B8, colorsAddr 0x4C62C2, 75 bits 1 seguidos de zeros.

    7.6 Q5 — receita para gerar o animado¶

    Partindo de um .acf estático válido e de N quadros já codificados em STC (N × slice_bytes, slice_bytes = ceil(w/4)*ceil(h/4)*16):

    1. Localizar o registro do slot. No bloco da página do slot, a tabela TextureClass[] está no fim do bloco; o registro da imagem é o que tem mTexAttr>>4 in (0x0,0x1) e TexWidth × TexHeight = tamanho do widget. TexAddr, SingleSliceSize, SliceFlagsHeaderAddr e o trailer atual (16 B) saem dele.
    2. Delta d = (N−1)*slice_bytes + trailer_novo − trailer_velho (trailer(n) = 8 + 4*ceil(n/16) arredondado para 16).
    3. Remontar a área de textura [0, StartOfConfigdata):
    4. [0, TexAddr) intacto;
    5. N quadros em TexAddr + i*slice_bytes;
    6. trailer novo em TexAddr + N*slice_bytes: flagsAddr = tr+8, colorsAddr = tr+8+2*ceil(N/16), bitmap com N bits 1 (MSB-first em cada u16), área de cores zerada, padding até 16;
    7. toda textura (e trailer) com addr > TexAddr deslocada em +d, na mesma ordem (o gerador reempacota assim; nenhum alinhamento extra é usado);
    8. completar até StartOfConfigdata_novo com o padding (qualquer byte — o firmware não lê; para reproduzir o gerador, copie o padding antigo truncado).
    9. StartOfConfigdata_novo = arredonda_16K(fim_da_última_textura + trailer + padding). Na prática: o arquivo final tem que continuar 8 + k*16.384; o padding absorve a diferença (aqui sobraram 6.928 B).
    10. Patchar os registros de textura de todas as páginas afetadas: TexAddr += d e, se SliceFlagsHeaderAddr != 0, += d; no registro do slot, SliceFlagsHeaderAddr = TexAddr + N*slice_bytes.
    11. GifSliceNum = N no bloco do widget (WDG_u16_userVariables[+11], aqui bloco+0x17E). GifNowIdx/GifNowTime = 0. GifID fica como está.
    12. Recalcular o CheckCode de cada página cujo bloco foi tocado (0xA55A5AA5 ^ XOR(words do bloco)) no descritor ConfigInfo+284+CfgStringSize+i*56+8.
    13. Header/ConfigInfo: @0, TotalSize, TotalTextureSize (+delta), @8 = TotalTextureSize/2, e por último o checksum @4 e o footer 0xA55A5AA5.
    14. Validar com ./acf_inspect.py (é o que o firmware checa).

    Validação da receita (reconstrução)¶

    Implementei os 9 passos acima em Python e comparei com o gif75.acf original:

    variante entrada bytes divergentes
    B — estrutura estático + os 75 quadros do gif75 + o conteúdo das páginas 5/6 do gif75 5.160.968 10
    A — estrita estático + os 75 quadros (conteúdo das páginas 5/6 vem do estático) 5.160.968 53.326

    A variante A só diverge por conteúdo: 53.315 dos 53.326 bytes são os pixels da página 5 (o estático tem outra imagem ali — §7.1); os 11 restantes são os mesmos 10 de B mais 1 byte de checksum.

    Os 10 bytes de B, um por um:

    offset bytes o que é
    0x4..0x6 3 checksum do arquivo — consequência dos outros (recalculado sobre bytes diferentes)
    0x4E41FA 1 CheckCode da pág. 2 — consequência do byte seguinte
    0x4E7136 (cfg+0x3136 = pág.2 bloco +0xE52) 1 padding do registro TextureClass (o struct acaba em +45, useCanvasPoint; +46/+47 são padding e o firmware não lê)
    0x4E91BE, 0x4E923A (pág. 7, bloco +0x92 e +0x10E) 2 campo u16 não decodificado, duplicado em CanvasClass/SubCanvasClass (204 nas págs. 4/5/6; 79→83 na pág. 7). As duas ocorrências mudam igual → o CheckCode da pág. 7 não muda (o XOR das duas variações se anula)
    0x4EC000..0x4EC002 (cfg+0x8000) 3 lixo de heap do gerador nos 4 bytes antes do footer (0x8FF2E8C4 vs 0x8FF0E2D4)

    Ou seja: nenhum byte de estrutura divergiu. Dos 10: 4 são lixo/padding do gerador que o firmware não lê (1 em TextureClass+46, 3 antes do footer), 2 são um campo interno ainda não decodificado e 4 são checksums que são função dos outros bytes.

    7.7 O que o minitela_patch.py precisa mudar¶

    Hoje (minitela_patch.py:103-120) ele abre o template, sobrescreve data[addr:addr+slice] com a textura nova (mesmo tamanho, mesmos offsets), chama codec.set_checksum e grava. Isso funciona porque a área de textura não é coberta por nenhum checksum e nada se move.

    Para suportar N > 1 quadros é preciso:

    1. Deixar de ser patch in-place. Com N > 1 o arquivo cresce e tudo depois do slot anda; o mínimo é a rotina de "remontar a área de textura + relocar" do §7.6 (passos 2-5). Alternativa mais simples e mais segura: manter um template por número de quadros (N=1, N=16, N=32, ... usam trailers de tamanhos diferentes) e só sobrescrever os quadros — mas o alvo continua sendo o registro certo, não um offset fixo.
    2. Escrever o trailer de fatias (SliceFlagsHeaderAddr) com o tamanho certo (16 B até 32 fatias, 32 B até 96, …) e o bitmap todo em 1 para fatias de imagem.
    3. Relocar TexAddr e SliceFlagsHeaderAddr de todas as texturas com addr > slot_addr (aqui as páginas 5 e 6), atualizando os registros nos blocos.
    4. Atualizar GifSliceNum no bloco do widget (não existe campo equivalente na página: DynamicPageCfgClass não tem contagem de quadros).
    5. Recalcular o CheckCode de toda página cujo bloco mudou (0xA55A5AA5 ^ XOR). Este é o ponto que hoje não existe e que faria o firmware entrar no do{}while infinito de AHMIInterface.cpp:1387-1423 se ficasse para trás.
    6. Atualizar o header: @0, TotalSize = tamanho−8, TotalTextureSize += d, @8 = TotalTextureSize/2, e só então @4 (checksum) — nessa ordem.
    7. Manter 8 + k*16.384: o padding do fim da área de textura é a variável de ajuste; StartOfConfigdata continua múltiplo de 16 KB e DynamicPageSize não muda.
    8. Não copiar o padding nem os bytes TextureClass+46/+47 do template novo — são lixo de heap do gerador; qualquer valor serve (mas, se quiser reprodutibilidade byte a byte, copie do template truncado, como na reconstrução).
    9. Ler os quadros do GIF respeitando o GifInterval implícito: o firmware consome GifSliceNum fatias em sequência a ceil(GifInterval/30) ticks cada (ActionProcessor.cpp:2405-2437), então o campo GifInterval do bloco tem que acompanhar o atraso do GIF se ele mudar.

    Engenharia reversa do primeiro firmware GC9002 real — flash_download.elf¶

    Companheiro do RE-acf.md. Aqui o alvo não é o container .acf, é o outro lado: o firmware que o fabricante usa para gravar a flash QSPI NOR que mapeia em 0x08000000 — o mesmo barramento onde mora o Texture.acf (0x08100000).

    Método: 100% estático. O .elf não foi executado, nada foi gravado na minitela. Ferramentas: llvm-readelf/llvm-dwarfdump, Capstone 5 (rv32 + RVC) e Ghidra 12.2 (projeto work/fw142, ignorado pelo git). Decompilado completo em /tmp/opencode/fw/decompiled.c (efêmero); os endereços citados bastam para refazer.

    Regra deste documento: todo achado tem coordenada. O que é leitura de código aparece como símbolo @ 0xADDR; o que é inferência está marcado HIPÓTESE; o que não dá para saber por este binário está marcado NÃO DOCUMENTADO.

    Não é o firmware da minitela. É o flash algorithm no formato do C-Sky CDK (FlashDev.c + driver.c, ver DW_AT_decl_file de FlashDevices e das funções flash*), que a IDE carrega em SRAM, executa e comanda por uma struct em memória. É o código que o fabricante usa quando grava a placa na fábrica/upgrade.

    O binário é linkado para uma SRAM de 32 KB em 0x02000000 (__ram_end = 0x02008000, .bss termina em 0x02007460, heap 0x02007460–0x02008000). O HyperRAM (HYPER_DATA_BASE 0x20000000) é inicializado em SystemInit (0x02002ac8 → HAL_HYPER_Init @ 0x02001d1a) mas não é usado como memória por este algoritmo — só os registradores dele são tocados.

    Não há sistema operacional de verdade em uso: pxReadyTasksLists/vTaskSwitchContext existem porque o FreeRTOS é linkado (port RISC-V), mas o main (0x02000630) é um laço while(1) { __bkpt_label(); switch(g_func) ... }.

    2.2 Só declarado (macro/IRQ), sem nenhum acesso no código¶

    Estes endereços vêm de .debug_str (dump de macros do -g3) e não aparecem em nenhum lui do .text. Servem como mapa do SoC, não como uso:

    periférico endereço
    DQSPI_BASE / DQSPI_DATA_BASE 0x4010C000 / 0x31000000 (só o clock em QSPI_MspInit)
    CRC32_BASE 0x40108000 ← ver §5
    DCACHE_BASE 0x40102000
    UART_BASE (UART0/1/2) 0x40001000, +0x1000, 0x4000E000
    GPIOA_BASE / GPIOB_BASE 0x4000A000 / 0x4000B000
    WDT_BASE / RTC_BASE / VIDEOCAP_BASE 0x40106000 / 0x40105000 / 0x4010B000
    SPI0/1/2, I2C0/1, I2S 0x40007000, 0x4000C000, 0x4000D000, 0x40005000, 0x40006000, 0x40008000
    CANFD_BASE / DMA_BASE / ETH_BASE 0x40000000 / 0x50200000 / 0x50400000
    CLIC_BASE 0xE0800000
    SYSMAP_BASE / TCIP_BASE / DCC_BASE 0xEFFFF000 / 0xE000E000 / 0xE4010000

    Sem UART de verdade: putchar @ 0x02001b34, fputc @ 0x02001b0c e printf @ 0x02001b38 são stubs que retornam 0; puts @ 0x02001b10 só chama fputc. As strings de erro (csi_spiflash_program ERROR. em 0x02002c80 etc.) existem e são referenciadas, mas nunca saem do chip. Nenhum GPIO é configurado para a flash: QSPI_MspInit @ 0x02000b8e só habilita clock no RCC (nada de GPIOA/B) — o que sugere pinos dedicados no pacote (HIPÓTESE, não há muxing no código).

    Tabela de vetores (__Vectors @ 0x02002e00, 47 words, .vectors off 0x3200):

    • [1..2] idem, [3] tspend_handler @ 0x02000300, [7] CORET_IRQHandler @ 0x02000ab4
    • [16..43] handlers por periférico, na ordem: 16 CANFD, 17 UART0, 18 UART1, 19 UART2, 20 TIM0, 21 TIM1, 22 SPI0, 23 I2C0, 24 I2C1, 25 SPI1, 26 I2S, 27 GPIOA, 28 GPIOB, 29 SPI2, 30 ADC, 31 WDG, 32 RTC, 33 CQDPI, 34 VIDEO_CAP, 35 DMA, 36 OTG, **37 AHMI**, 38 DISPLAY, **39 CRC32**, 40 MOTOR, 41 MAC, 42 EXTENSION, 43 DQSPI

    Coordenada interessante para o projeto: existe um vetor de IRQ chamado AHMI (0x02000b6e, índice 37). O SoC tem um bloco AHMI. NÃO DOCUMENTADO o que ele faz — o handler neste binário é mret. (Registro: irq_num = 0x21 em csi_qspi_init aponta para o índice 33, que a tabela nomeia CQDPI; a numeração IRQ do CQSPI não bate com a ordem nominal da tabela — não documentado, possivelmente CLIC source ≠ índice.)

    3. Sequência de erase/write¶

    3.1 Protocolo do CDK (entry → funções)¶

    O main (0x02000630) lê uma struct de comando em SRAM e despacha por g_func:

    símbolo endereço papel
    g_checksum 0x020040c4 argumento de flashChecksum
    g_dstAddress 0x020040c8 endereço na flash (ex. 0x08100000)
    g_error 0x020040cc retorno
    g_flashID 0x020040d0 saída do comando 0
    g_func 0x020040d4 comando 0..6
    g_length 0x020040d8 tamanho
    g_rwBuffer 0x020040dc buffer de 8192 bytes (a transferência é em blocos ≤ 8 KB)

    Comandos: 0 ID, 1 program, 2 read, 3 erase, 4 chip-erase, 5 uninit, 6 checksum (main, casos em 0x02000676..0x02000742).

    Wrapper do CDK, driver.c (todas com tDst = dst - (16 << 23) = dst - 0x08000000, confirmado pelo DW_AT_GNU_call_site_value em 0x00003878):

    função addr observação
    flashInit 0x0200075e chama csi_spiflash_qspi_init(&spiflash, 0, NULL); erro = -200
    flashProgram 0x0200078a se dst - 0x08000000 > 0x1000000 → memcpy puro e retorna 0 (endereço fora da flash = "grava" em SRAM/HyperRAM); senão csi_spiflash_program
    flashRead 0x020007ea mesma guarda; flashRead(dst, src, len) com src = flash
    flashErase 0x0200084e mesma guarda — fora da janela retorna 0 sem fazer nada; erro -1
    flashChipErase 0x0200088a -1
    flashChecksum 0x020008b0 stub: return 0
    flashID 0x02000786 stub: return 0
    flashTest 0x020008b4 stub
    spiflash 0x020060dc csi_spiflash_t de 204 bytes (.bss)

    Nota para o RE-acf.md: flashChecksum devolver 0 sempre significa que nem o caminho de gravação do fabricante valida checksum algum — corrobora o FATO 7 ("o firmware não valida checksum"). O checksum do .acf é calculado/validado em outro lugar (ou em lugar nenhum).

    3.2 ERASE — a cadeia real¶

    flashErase(0x0200084e)
 └─ csi_spiflash_erase(0x02001856)            ; só aceita bus QSPI; SPI → CSI_UNSUPPORTED
     └─ qspiflash_erase(0x020016e8, SECTOR_ERASE)

    qspiflash_erase (decompilado com nomes do DWARF: erase_addr, erase_end_addr, erase_sectors, erase_size, erase_opcode):

    1. csi_qspi_write_protection_ctrl(qspi, false) → limpa bit1 de 0x40100000+0x58 (qspi_write_protection_ctrl @ 0x0200252a).
    2. erase_size e erase_opcode saem da tabela SFDP lida na init (por tipo: SECTOR_ERASE→sector_size+opcode.erase_sector; HALF_BLOCK_ERASE→block_size/2+erase_half_block; BLOCK_ERASE→block_size+erase_full_block; CHIP_ERASE→capacity+erase_chip).
    3. erase_sectors = ceil(size / erase_size).
    4. Laço while (i < erase_sectors && (addr & 0xFFFFF000) <= offset + size):
    5. qspiflash_send_opcode(spiflash, opcode.write_enable) → WREN 0x06 (qspiflash_send_opcode @ 0x02000ff6: csi_qspi_command_t só com instrução, sem endereço/dados → csi_qspi_send);
    6. command.address.size = addr & 0xFFFFF000 (o campo se chama size na union, mas carrega o valor do endereço) ⚠️ o endereço é truncado em 4 KB, sempre, mesmo que erase_size seja 64 KB (qspiflash_erase, 0x02001780–0x0200178c: lui a3,0xfffff; and a3,a5);
    7. csi_qspi_send(qspi, &cmd, NULL, 0, -1) → qspi_send_cmd @ 0x02002578 (programa 0x90/0x94, 0x90 |= 1 para disparar, espera 0x90 & 2 limpar);
    8. faz polling do status: csi_spiflash_read_reg(spiflash, opcode.read_sr1, &SR, 1) em laço enquanto SR.SR1 & 1 (WIP) ≠ 0;
    9. addr += erase_size, i++.
    10. csi_qspi_write_protection_ctrl(qspi, true).

    csi_spiflash_chip_erase (0x02001872) é o mesmo caminho com type = CHIP_ERASE, offset = 0, size = 0: WREN + opcode erase_chip (= 0x60 fixo, ver §3.4) + poll.

    3.3 PROGRAM — a cadeia real¶

    flashProgram(0x0200078a)
 └─ csi_spiflash_program(0x02001654)
     ├─ csi_qspi_write_protection_ctrl(qspi, false)
     ├─ csi_qspi_direct_send(0x02000dec)        ; "direct" = modo write-through da janela
     │   ├─ csi_qspi_direct_mode_config(0x02000d2e, QSPI_WRITE)
     │   │    → qspi_set_spi_mode_base(0x020022f2)  (0x04/0x08)
     │   │    → qspi_cfg_reads/writes(0x020021a0)   (opcode de write no 0x08)
     │   │    → qspi_cfg_addr_bytes / page_size / block_bytes (0x14)
     │   └─ qspi_direct_access_write(0x02002828)
     │        → **stores de 32 bits em `0x08000000 + offset`**
     ├─ loop: csi_spiflash_read_reg(opcode.read_sr1) até WIP=0
     ├─ csi_qspi_write_protection_ctrl(qspi, true)
     └─ csi_qspi_direct_mode_config(qspi, cfg, QSPI_READ)   ; volta pro modo XIP

    Detalhes que importam:

    • Escrita não usa comando explícito: qspi_direct_access_write faz *(uint32_t*)(remap_bus_base + offset + i) = *(uint32_t*)(src + i) e o remap_bus_base é 0x08000000 (cqspi_dev_cfg @ 0x02002df0). Quem traduz store em página de flash é o controlador, configurado com o opcode de page program.
    • WREN explícito não aparece no caminho de program (só no de erase). HIPÓTESE: o CQSPI emite 0x06 automaticamente antes de cada página; o que o código faz é só habilitar/desabilitar a proteção de escrita do controlador (0x58 bit1). NÃO DOCUMENTADO — o .elf não mostra o WREN da página.
    • O baud rate é rebaixado para div = 8 durante a escrita e restaurado no fim (qspi_get_baud_rate_div/qspi_set_baud_rate_div, 0x02002238/0x02002248). Com PLL 480 MHz (SystemInit), leitura roda a 120 MHz (get_qspi_freq_max @ 0x02000eda devolve 120 MHz com PLL 480 MHz, 108 MHz com 432 MHz, 72 MHz com 288 MHz) e a escrita a ~60 MHz (480/8) — valor derivado, não constante no binário.
    • O page_size da SFDP é programado no hardware (0x14 bits 4–15); é o controlador que quebra a escrita em páginas. O software não alinha nada.
    • Bug/limitação do laço de erase: a condição de parada usa (addr & 0xFFFFF000) <= offset + size; um range que termina no meio de um setor apaga o setor inteiro. Some com o truncamento de endereço e o resultado é: erase de 1 byte pode apagar 4 KB.

    3.4 Comandos JEDEC — de onde vem cada opcode¶

    Tudo isso é montado em SFDP_flash_read_parameter @ 0x0200107c (é a função que enche flash_prv_info e spiflash->opcode, structs descritas em 0x000033c3 e 0x0000353e do DWARF).

    Fixos no código:

    comando opcode coordenada
    Write Enable 0x06 (spiflash->opcode).write_enable = 6
    Write Enable VSR 0x06 ou 0x50 depende de SFDP DWORD0 bit 0x10
    Read SR1 / SR2 / SR3 0x05 / 0x35 / 0x15 idem
    Write SR1 / SR2 / SR3 0x01 / 0x31 / 0x11 idem
    Chip Erase 0x60 (spiflash->opcode).erase_chip = 0x60
    Enable Reset / Reset 0x66 / 0x99 csi_spiflash_qspi_init @ 0x020018de
    SFDP Read 0x5A qspiflash_get_SFDP_by_addr @ 0x02001036
    Enter 4-byte address 0xB7 só se SFDP+0x3C bit24 e addr_4_byte → >128 MB
    Mode-444 disable / enable 0xFF/0xF5 e 0x38/0x35 SFDP+0x38

    Lidos da SFDP (tabela JEDEC Basic Flash Parameter, ponteiro em SFDP+0x0C):

    campo origem valor típico (inferência da norma SFDP)
    4 KB erase opcode byte1 do DWORD em +0x00, se (dword & 3) == 1 0x20
    sector_size 1 << (byte0(+0x1C) & 0x1F) 4096
    erase_sector opcode byte1 de +0x1C 0x20
    erase_half_block opcode byte3 de +0x1C 0x52 (32 KB)
    block_size 1 << (byte0(+0x20) & 0x1F) 65536
    erase_full_block opcode byte1 de +0x20 0xD8 (64 KB)
    page_size 1 << ((byte(+0x28) >> 4) & 0xF) 256
    capacity DWORD em +0x04 (densidade em bits; MSB→1<<(n-3)) 16 MB
    opcode/dummy de leitura DWORD em +0x00 (1-4-4 / 1-1-4 / 1-1-2) 0xEB / 0x6B / 0xBB
    opcode de page program derivado do modo de escrita: 0x02 (1-1-1), 0x32 (1-1-4), 0x3E (1-4-4) —

    Validado na init: SFDP magic 0x50444653 em 0x0 e revisão menor ≤ 1 em 0x4; o ponteiro da tabela JEDEC precisa ser < 0xFF (macro CSI_IS_SFDP_PTP_BASE_ADDR(ADDR) ((ADDR) < 0xFF), presente em .debug_str).

    Fluxo de clock da init: reset (0x66,0x99) e leitura da SFDP a 2.5 MHz (get_qspi_freq_min = PLL/0xC0), depois sobe para 120 MHz e roda qspi_adapted_capture @ 0x020028fc, que varre delays de amostragem com o comando 0x9F (Read JEDEC ID) — é a única leitura de ID de flash no binário inteiro. No fim a init lê 8 bytes do endereço 0 e exige que a leitura funcione (csi_spiflash_read(spiflash, 0, buf, 8)).

    3.5 Alinhamento e tamanho de setor — resumo¶

    item valor base

    5. CRC32 em 0x40108000¶

    Fatos, todos verificáveis:

    fato coordenada
    CRC32_BASE (0x40108000UL) existe macro em .debug_str
    CRC32_Typedef/CRC32 são referenciados como tipo/macro .debug_str (CRC32 (CRC32_Typedef *)CRC32_BASE)
    CRC32_IRQn e CRC32_IRQHandler existem .debug_str; handler em 0x02000b76 = mret (4 bytes)
    o vetor 39 aponta para ele __Vectors[39] = 0x02000b76 em 0x02002e9c
    nenhum acesso a 0x40108000 no código todos os lui do .text dão 0x2004/0x2006/0x2007/0x1000/0x40200/0xe0800/0xf8000/0xe4e2/0xe000c/0x40100/0x40101/0x40102/0x4010c/... — não existe 0x40108

    Portanto:

    • O polinômio não é observável neste binário. NÃO DOCUMENTADO. Não há rotina de CRC, nem escrita de init/poly/xorout. Só dá para dizer que o bloco de hardware existe no SoC e que o flash_download.elf o ignora completamente.
    • Não é o checksum do .acf. O .acf usa XOR de words de 32 bits LE, pulando o próprio campo e o footer 0xA55A5AA5 (RE-acf.md FATO 6). Isso não é CRC32 sob nenhum polinômio: não tem polinômio, não tem init/xorout, não tem reflexão de bits, e o invariante medido ("XOR de todas as words == 0xA55A5AA5") é uma propriedade de XOR (comutativo, ordem-independente), não de CRC (onde o resíduo é fixo e não depende do dado — e aqui o resíduo é o magic do rodapé).
    • Corroboração independente: flashChecksum @ 0x020008b0 é li a0,0; jr ra. O caminho de gravação do fabricante não valida checksum nenhum. Se o CRC32 de hardware é usado em algum lugar, é no firmware AHMI (que não temos), não aqui.

    6. O que isso explica sobre a minitela¶

    1. 0x08000000 é literalmente CQSPI_DATA_BASE. O Texture.acf em 0x08100000 é o offset 0x100000 da mesma NOR, na mesma janela que o CPU lê como memória normal. Leitura de textura é XIP: csi_spiflash_read só faz qspi_remap_addr(dev,0) e lê 0x08000000 + offset (qspi_direct_access_read @ 0x02002762). Não existe comando de leitura por chunk no caminho quente.
    2. Gravar é sempre erase-de-setor + page program. Não há escrita parcial em NOR. Qualquer alteração, mesmo de 1 byte, obriga a apagar 4 KB e reescrever. Isso explica mecanicamente o dano colateral do FATO 7 do RE-acf.md: patch em 753192 cai no meio de um setor e o setor inteiro vai junto.
    3. Pior ainda: o driver trunca o endereço de erase em 4 KB (addr & 0xFFFFF000) e o laço continua enquanto (addr & 0xFFFFF000) <= offset+size. Se o firmware AHMI usar esta mesma HAL (mesmo SDK, strings ../../../csi_driver/csi_spiflash.c em .debug_str), um "erase de N bytes" apaga ceil(N/4096) setores a partir do setor que contém o primeiro byte. HIPÓTESE para o firmware da tela; FATO para este binário.
    4. 16 KB do container = 4 setores exatos. O alinhamento do .acf não é exigência da flash; é decisão do container que, por coincidência (ou não), casa com 4 setores.
    5. A transferência do app é em blocos ≤ 8 KB (o g_rwBuffer do CDK tem 8192 bytes). Isso é consistente com o UPLOAD_DATA fatiado do AHMI observado no minitela_ctl.py.
    6. A geometria é lida da SFDP em runtime, não de tabela de IDs. Consequência prática: o mesmo firmware serve 4/8/16/32 MB; não dá para inferir o part pelo firmware, só pelo SFDP/JEDEC ID do aparelho.
    7. O caminho de gravação do fabricante não verifica checksum (flashChecksum stub). Bate com o teste do RE-acf.md em que um .acf com checksum antigo continuou bootando.

    O que continua em aberto¶

    • Qual é a flash (fabricante/capacidade). Precisa de 0x9F no device — operação humana, com recuperação armada. Este .elf não responde.
    • O firmware AHMI usa esta HAL? As strings de build (csi_driver/csi_spiflash.c, gc9002_ll_qspi.c, gc9002_hal_hyper.c) mostram que o SDK é o mesmo; a prova exigiria o dump do firmware da tela.
    • Polinômio do CRC32 de hardware (0x40108000): não está em nenhum artefato que temos. Se o firmware AHMI usar, aparece no dump dele.
    • AHMI_IRQHandler (vetor 37): o SoC tem um bloco AHMI com interrupção própria. Saber o que ele faz ajudaria a mapear o protocolo, mas neste binário o handler é mret.
    • Devs[0].Length = 0x30000000 e TotalSize = 0x80000: campos inconsistentes do descritor; não documentado como o CDK os usa.
    • WREN no page program: o .elf não emite; presumo que o controlador emita (HIPÓTESE). Um teste no hardware (escrever e ler o SR1 antes/depois) resolve, mas é operação humana.

    11. Entrada no bootloader¶

    Resposta curta. Neste SDK a entrada no bootloader é uma janela de tempo no boot, não um flag: o bootloader sempre roda primeiro, espera um handshake 0x0080 por can_uart_wait_ms (default 500 ms) e, se ninguém falar, salta para o app. Não há GPIO, flag em RAM no-init, campo em upg_cfg.bin nem comando que mude isso (§11.3). O firmware de produção tem um caminho extra — 0x0071 põe o app em modo download sem reset —, mas isso não está neste SDK. E, mesmo entrando no bootloader, não há dump: o 0x0083 não tem handler (§12).

    11.1 Por que o bootloader sempre roda¶

    O bootloader é a imagem em 0x08000000 (Bootloader.elf: entry 0x08000000, .text 0x08000000+0x2FC54). O .bin de produção tem um header de 16 B gerado por boot_headInfo_add.sh:

    0x00 u32 size     0x04 u32 CRC32(code)
0x08 u32 magic 0x48494948    0x0C u32 0
0x10 code

    O app fica em 0x08040000 e o seu primeiro setor é o "cartão de visita" lido pelo bootloader (od do GC9002AHMI.elf, VMA 0x08040000 = offset 0x400):

    0x08040000  "1.10.20_build_2025.07.02.10.45"   <- CPU1_VERSION_ADDRESS
0x08040020  "Jul 22 2025"                      <- compile date
0x08040030  "16:54:23"                         <- compile time
0x08040040  "GC9002"                           <- CPU1_APP_COMPILE_ADDR_STORE_ADDR
0x08040060  entry (APP_FUNCTION_START_ADDR)

    main() do bootloader: CFG_vInit() → HardwareInit() → SoftwareInit() (UPG_Main_vInit) → scheduler (main.c:89-101). A primeira coisa que a task de upgrade faz é UPG_SUBSM__vGetComMode() (upgrade_subsm.c:951).

    can_uart_wait_ms 500 janela de 500 ms
    UartCfg ch=2, tx=PB9, rx=PB8, baud=3 UART2 @ 115200, cfg_ca.c:203-226,294-313, upgrade_uart_platform.c:134-139

    Validação do upg_cfg: magic + version + soma de 16 bits dos bytes após o header (cfg_c1.c:47-73); se o bloco em 0x080F7000 falhar, o bootloader usa o blob compilado (cfg_c1.c:20-35) — nunca fica sem config.

    11.3 O que NÃO existe (procurei e não há)¶

    mecanismo situação
    flag em RAM no-init UPG_u32CanUartUpgFlag foi desativado: static uint32_t e o __attribute__((at(...))) está comentado (upgrade_subsm_passive.c:24-25). Não sobrevive a reset
    GPIO / boot pin HardwareInit() não lê pino nenhum (main.c:20-81); UsbCfg tem usb_ctrl_enable_port/pin e insert_check (cfg_autogen_ct.h:65-74) mas os getters (cfg_autogen_ca.c:252-290) não são usados pelo upgrade
    comando "reboot to upgrade" o app tem MODULE_INFO_REG_SYSTEM_RESET = 10056, mas o handler está com o corpo comentado (GeneralCom_Moduleinfo.c:74-80) → não reseta
    flag em upg_cfg.bin os campos são só cfg_uart/cfg_can/cfg_sd/cfg_usb/can_uart_wait_ms (cfg_autogen_ct.h:17-25). Não há one-shot de boot
    comando do app p/ modo download não existe no SDK. No firmware de produção é o 0x0071 com payload 0x10 (minitela_ctl.py:314), que troca o estado de 0x20 (UI) para 0x10/0x11 (download) sem reset — ou seja, o app de produção tem um modo de recepção embutido, que este SDK não tem
    watchdog / reset reason nada no caminho do bootloader
    upg_cfg gravável por comando sim: upg_cfg.bin é destino válido (upgrade_ci.h:159) — mas isso muda o futuro, não entra em modo upgrade

    11.4 Procedimento (válido se o bootloader da minitela for este)¶

    1. Reset (power cycle; um reboot por software também serve, porque o bootloader é quem roda primeiro).
    2. Em ≤ 500 ms (can_uart_wait_ms), enviar 0x0080 no canal configurado — por default UART2, PB9=TX/PB8=RX, 115200 8N1 (não é o CDC-ACM).
    3. Receber 0x00C0 + u32 64. A partir daí a SM passiva fica em CanUart_Run (upgrade_subsm_passive.c:126-152) e não salta mais.
    4. 0x0081 {addr, size} com addr idêntico a um destino da tabela (§9.4); 0x0082 em blocos de ≤ 64 B; 0x008F no fim.
    5. 0x008F derruba o bootloader para o app — não existe "ficar no bootloader".

    11.5 Risco¶

    • Não dá para dumpar por aqui: não há comando de leitura (§12). O melhor que o protocolo faz é responder 4 bytes de resultado.
    • 0x0081 apaga antes de receber (upgrade_passive.c:335). Um 0x0081 para Texture.acf abortado deixa 0x08100000 apagado → tela sem textura (recuperável repetindo o download). Um 0x0081 para cpu1.bin abortado apaga o app; o bootloader então não acha "1." em 0x08040000 (upgrade_c1.c:1384-1399) e vai para UPG_enMainSM_Error (upgrade_subsm.c:1076-1087), que não salta — só volta a funcionar pelo próprio bootloader (UART). É o cenário de "tijolo recuperável".
    • bootloader.bin é destino válido e escreve em BOOTLOADER_SAVE_ADDR; com bFlagUpgWithSelfUpg = TRUE (upgrade_ci.h:149) o bootloader se sobrescreve em 0x08000000 no JumpToApp (upgrade_sm.c:296-307). Aqui o tijolo é real.
    • upg_cfg.bin também é gravável: um cfg_uart=0 + reset fecha a porta de recuperação (sobra só SD/USB-host).
    • O addr do backup do bootloader depende de TextureFlashSize (upgrade_sm.c:161-168), que depende do JEDEC ID lido no boot (§12.3) — em part não reconhecido ele usa o default de 4 MB.

    12. Leitura de flash: veredito¶

    12.1 Não existe comando de leitura no SDK¶

    caminho comandos leitura de flash/memória?
    bootloader, AH…MI 0x0080/0x0081/0x0082/0x008F não
    bootloader, CAN/UDS SID 0x10, 0x11, 0x28, 0x64/0x66/0x67 ($SDK/projects/Bootloader/Source/CAN_Diag/SRV/SIDSource/) não (nem 0x22 ReadDataByIdentifier, nem 0x23/0x34/0x36/0x37)
    app, 0xA5/0x5A set/get de registrador AHMI (GeneralComExe.c:267,428,509,551) não — IDs 10000…11000 são estado/versão/backlight/RTC (GeneralCom_Moduleinfo.h:53-104); nenhum mapeia flash
    app, USB CDC nenhum (callback descarta, §9.1) não

    O único dado "de leitura" que o protocolo devolve são os 4 bytes de resultado (UPG_tunUartRplContent, upgrade_uart_platform.h:170-174): tamanho de pacote no handshake e código de retorno nos demais.

    12.2 UPG_CMD_UPLOAD — confirmado morto¶

    • Definição: upgrade_uart_platform.h:66 — #define UPG_CMD_UPLOAD (0x0083).
    • Uso: zero. O switch de UPG_UART_vParseCmd (upgrade_uart_platform.c:464-540) tem só 4 case e um default mudo.
    • Confirmação no objeto: no projects/Bootloader/Obj/core_upgrade_uart_platform.o, a seção .text.UPG_UART_vParseCmd (llvm-readelf -S: seção 129) desmonta para li a4,130 / bltu a4,a5,… / li a4,128 / li a4,129 — os casos 0x82, >0x82 (0x8F), 0x80 e 0x81. Não existe comparação com 0x83.
    • Nenhum handler em outro lugar: nm em todos os Obj/*.o do bootloader não devolve nenhum símbolo com "upload"; grep -rl UPG_CMD_UPLOAD só encontra o header e arquivos .o/.elf onde a string aparece no dump de macros do -g3 (.debug_macro), não como código. O mesmo vale para o app (Obj/*.o): nada.
    • Sem handler em .a: o Bootloader.map só puxa libm.a/libc (Bootloader.map:77-88); nenhum arquivo de biblioteca implementa upgrade.

    Nota que corrige a §4/§6 deste documento: qspi2_CheckTextureFlashType (texture_flash.c:496-560) é a tabela de IDs do firmware de aplicação — a mesma família FLASH_ID_IS_* do flash algorithm, agora com nome de part no comentário (W25Q128/GD25Q127/BY25Q128/XM25QH128/ZB25VQ128, W25Q64/..., W25Q256/GD25Q257, XM25QH32/ZB25VQ32, NAND WB/GD/DS). E o bootloader (csi_hal_driver_flash.c:90-160) usa uma lista mais estreita e mascara o 4º byte: um Winbond 0x1840EF não está na lista do bootloader (só 0x184020 e 0x18405E) → TextureFlashSize fica no default de 4 MB e o DRIR (fast read) não é programado. HIPÓTESE: o part da minitela é um dos reconhecidos pelo app (senão a textura não renderizaria), e o bootloader de produção pode ter uma lista diferente desta do SDK.

    12.4 Veredito¶

    Não há caminho de software, neste SDK, para ler a flash pelo protocolo. O AH…MI é write-only (handshake + download + fim), o UPG_CMD_UPLOAD é uma constante órfã, e o USB CDC do SDK descarta o que chega. Para dumpar a flash sobram dois caminhos, ambos fora do escopo deste repositório: (a) SWD/JTAG com o CDK — o mesmo caminho que o flash_download.elf da §1-§8 usa, com o algoritmo de flash em RAM; (b) um firmware próprio rodando no chip. Se algum dia aparecer o dump do firmware de produção (o que responde em 0324:0324), aí sim vale procurar um case 0x0083 nele: o python já assume que ele existe (minitela_ctl.py:52-56) mas nada neste SDK confirma.
